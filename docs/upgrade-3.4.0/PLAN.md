# План апгрейда 3.3.2 → 3.4.0: весь контент апстрима V5.2–V5.6

План рассчитан на **новую сессию-лида с командой агентов**, которая работает без остановок. Что переносим, описано в [REPORT.md](REPORT.md), точные числа и `file:line` — в [notes/](notes/). Текущее состояние ведётся в [STATE.md](STATE.md); лид создаёт его на этапе 0 и обновляет после каждого шага.

## Цель и приоритеты

**Переносится всё.** Каждое изменение апстрима с V5.1 (база нашего порта) по V5.6 включительно, документированное и нет. Исключений по объёму нет.

При любом выборе приоритеты такие:
1. **Соответствие оригиналу V5.6:** поведение, числа, тексты.
2. **Работа на Anbernic RG34XX SP** (1 ГБ GDDR3L, muOS, ввод через gptokeyb). Оптимизация не должна менять игровой результат: урон, баланс и тексты остаются как в оригинале, а экономия идёт на эффектах, частицах, загрузке ресурсов и памяти.
3. **Все тексты на русском:** ни одной испанской или английской строки в ru-интерфейсе.

Наши собственные фичи, которых нет в оригинале, сохраняются как есть:
- натуры, капсулы способностей, TM, ежедневная лавка, второй стартовый приём;
- слияния без лимита за забег с причиной отказа;
- `perf_log`/`run_log`, слияние цифр урона `DMG_TXT_MAX`;
- ввод только с клавиш на хендхелде (`keys_only.gd`).

## Экономия и слежка за лимитами

1. **Модели.**
   - Лид — сессия на Opus.
   - Исполнители — `sonnet` по умолчанию.
   - `opus` только для 2A (ядро perf) и 4 (поимка): там сложная логика и риск регрессий.
   - Механика (проверка JSON, поиск ключей, сверка списков) — `haiku`.
2. **Контекст лида.** Лид не читает целиком `main.gd` (11 тыс. строк) и `menu.gd` (7 тыс.): только `grep -n` и диапазоны `sed -n`. Диффы агентов смотрит через `git diff --stat` и выборочно по функциям. Подробности держит в файлах (`STATE.md`, `keys/`), а не в чате.
3. **Промпты агентов** короткие. Вместо пересказа плана — ссылка на раздел PLAN.md и на нужный `notes/`/`diffs51` файл. Пункты «что трогать» и «что не трогать» обязательны.
4. **Не больше 3 исполнителей одновременно.** Агент, который уже держит контекст файла, получает следующую задачу по нему через `SendMessage`; новый с нуля не запускается.
5. **Отчёты агентов:** не больше 20 строк — изменённые функции, ключи сейва, новые строки, результат headless-проверки. Без кода.
6. **Учёт расхода.** После каждого этапа лид вызывает `mcp__ccd_session_mgmt__get_usage` и пишет расход в таблицу «Расход» в `STATE.md`. Если окно лимита заполнено больше чем на ~85%:
   - не запускать новых агентов;
   - довести текущее слияние и записать `STATE.md`;
   - дальше по разделу «Без остановок».
7. **Без лишних прогонов в фазе I:** только headless-загрузка. Прогоны smoke/matrix/soak — один раз в фазе II и точечно в фазе III.

## Без остановок

- Сессию запускать через `/loop` с промптом из `SESSION_PROMPT.md`. Каждая итерация:
  1. читает `STATE.md`;
  2. выполняет следующий незакрытый шаг и обновляет `STATE.md`;
  3. затем `ScheduleWakeup` для продолжения или `stop`, если дошли до «ждём ок пользователя».
- **При упоре в лимит:** записать `STATE.md` и запланировать `ScheduleWakeup` на 1800–3600 с. Следующая итерация продолжит с того же места.
- **Если агент упал или вернул мусор:** один повтор с уточнённым промптом. Если снова неудача, лид делает сам или дробит задачу. Пункт ставится в «Проблемы» `STATE.md`, работа идёт дальше.
- **Конфликт слияния:** решает лид. Если конфликт в чужой функции, сохраняются обе правки.
- **Пользователю ничего не задаётся** до финала фазы IV.
